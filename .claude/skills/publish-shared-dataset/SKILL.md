# Publish Shared Dataset

## Trigger and boundaries

Treat plain-language requests such as "add this dataset," "upload this file,"
"put this data in shared-datasets," or "publish this" as official manual
dataset intake requests unless the user explicitly says scratch-only,
diagnostic-only, or no publication workflow. Do not satisfy those requests by
copying the supplied file to GCS alone.

The deliverable is a reviewable proposal: approved artifacts, asset metadata,
generated catalog/READMEs, generation-safe staging and an immutable reviewed
publish plan. A failed required artifact is a blocker, not a successful upload.
Read `AGENTS.md` first. Use `uv run`; keep generated bytes outside the repo under
`docs/standards/local-temp-workspaces.md`. Load `gcp-shared-datasets` before any
remote inspection/write, and `protected-terraform-apply` before infrastructure
or access-tier mutations. Read only the reference for the selected route below.
Canonical proposal routes also use [reviewed-proposal.md](references/reviewed-proposal.md).

Do not create a new top-level category or add a new canonical file format
without explicit human approval.
Do not infer human approvals from validator success. The concierge never stages
Git, commits, pushes, opens PRs, uploads objects, promotes data or applies Terraform.
Its `--help` and subcommand `--help` own flags; its output owns evidence schemas.
No script-source reading is required to use these tools.

## Route 1: First upload

Use for a new or under-specified asset. Read [first-upload.md](references/first-upload.md).
Discover the source and select an existing category/subcategory from
`catalog/categories.yaml`; classify the dataset itself, not its first consumer.
Set `SOURCE`, `CATEGORY`, `SUBCATEGORY`, `PROPOSAL_ID` from that evidence.
Use a stable issue/branch/proposal ID. Add verified metadata options from help;
choose `ACCESS_TIER` explicitly (`public` requires human approval).

```bash
uv run python scripts/publishing_concierge.py start --help
uv run python scripts/publishing_concierge.py start "$SOURCE" --category "$CATEGORY" --subcategory "$SUBCATEGORY" --request-classification canonical-publish --proposal-id "$PROPOSAL_ID" --access-tier "$ACCESS_TIER"
uv run python scripts/publishing_concierge.py next --state-file "$STATE_FILE" --json
uv run python scripts/publishing_concierge.py confirm --state-file "$STATE_FILE" --step "$STEP_ID" --evidence-json "$EVIDENCE_JSON"
uv run python scripts/publishing_concierge.py validate --state-file "$STATE_FILE"
uv run python scripts/publishing_concierge.py render-pr --state-file "$STATE_FILE" > "$WORK_DIR/pr-body.md"
```

`start` returns `state_file` and `current_step`; set `STATE_FILE` from the result.
Repeat `next` / external work / `confirm` for each step before `validate` and
`render-pr`. `next --json` returns `step_id`, `commands`, `evidence_schema`, and
`blockers`; use that schema, not a remembered checklist. Read the saved state
`plan` for `blocking_questions`, paths and `curator_field_options`.
Use [artifacts-and-metadata.md](references/artifacts-and-metadata.md) when building
or documenting; load `.claude/skills/update-feature-metadata-translations/SKILL.md`
when the translation decision applies. At staging, use the shared proposal's
catalog deploy rule even when concierge suggestions include catalog.json.
`validate.ready_for_pr` must be true with `errors: []`. `render-pr` writes the
immutable plan document as well as the matching PR fence. Follow the shared
proposal's commit/preflight/push/PR sequence; stop before protected publication.

## Route 2: Existing-asset update

Use when slug/contract already exist. Read [existing-asset-update.md](references/existing-asset-update.md)
and `docs/assets/{asset-slug}.md`. Preserve its paths, formats and identity.
If more than one asset could match, ask before staging bytes.
If the asset is cron-owned, do not bypass the job with a manual upload unless
explicitly asked for a corrective publish; use `deploy-scheduled-ingestion`.

```bash
uv run python scripts/gcs_asset.py list "$ASSET_URI"
uv run python scripts/gcs_asset.py stat "$LATEST_URI"
uv run python scripts/gcs_asset.py publish-release --help
uv run python scripts/gcs_asset.py publish-release --asset-slug "$SLUG" --release-date "$RELEASE_DATE" --publish-dir "$PUBLISH_DIR" --source-version "$SOURCE_VERSION" --dry-run > "$WORK_DIR/release-plan.json"
uv run python scripts/catalog_docs.py generate
uv run python scripts/catalog_docs.py check
uv run python scripts/catalog_docs.py export-readmes --output-dir "$WORK_DIR/readmes"
uv run python scripts/catalog_site.py --out "$WORK_DIR/catalog-web"
```

Build and validate replacements between `stat` and `publish-release`. Use that
command only for its supported single-object canonical formats; Zarr/multi-object
assets need an explicitly enumerated plan. Its JSON is a validation/destination
plan, not the promotion payload. Stage/stat each candidate using the shared
proposal, then `reviewed_dataset_plan.py prepare --publish "$PUBLISH_PLAN"`.
Do not run non-dry-run `publish-release` from a local human or agent terminal.

## Route 3: Preview upload

Use for disposable feature-preview data. Hand off to
[feature-preview](../feature-preview/SKILL.md); read its upload procedure only.
It owns complete bundles, preview URI validation, upload metadata and verification.

```bash
uv run python scripts/publishing_concierge.py start "$SOURCE" --category "$CATEGORY" --subcategory "$SUBCATEGORY" --request-classification preview-only --proposal-id "$PROPOSAL_ID" --release-date "$RELEASE_DATE" --preview-ref "$PREVIEW_REF" --access-tier private
uv run python scripts/publishing_concierge.py next --state-file "$STATE_FILE" --json
uv run python scripts/publishing_concierge.py confirm --state-file "$STATE_FILE" --step "$STEP_ID" --evidence-json "$EVIDENCE_JSON"
gh workflow run feature-preview-deploy.yml --ref "$PREVIEW_REF" -f preview_data_mode=preserve
uv run python scripts/publishing_concierge.py validate --state-file "$STATE_FILE"
uv run python scripts/publishing_concierge.py render-report --state-file "$STATE_FILE"
```

Run the workflow only at `preview-catalog-refresh`, after verified uploads.
`preview-upload` records exact preview URIs/generations; finish refresh and viewer
verification before `validate.ready_for_preview`. Do not render a production PR
or use production pending-publishes for preview loading.

## Route 4: Partial-publication recovery

Use after approved promotion partially ran. Read
[partial-publication-recovery.md](references/partial-publication-recovery.md).
Inspect the exact failed run/attempt and preserve its original plan/authority.
For an owned ingestion claim, use its owner recovery; never reset counters or
create a second transaction. Otherwise prepare a new unapproved proposal:

```bash
gh run view "$RUN_ID" --attempt "$ATTEMPT" --log-failed
uv run python scripts/publishing_concierge.py refresh-retry-plan --help
uv run python scripts/publishing_concierge.py refresh-retry-plan --plan "$PUBLISH_PLAN" --stat-gcs --stats-output "$WORK_DIR/retry-stats.json" --output "$WORK_DIR/retry-plan.json" --summary-output "$WORK_DIR/retry-summary.json"
uv run python scripts/reviewed_dataset_plan.py prepare --publish "$WORK_DIR/retry-plan.json" > "$WORK_DIR/pr-body.md"
```

The helper verifies staged source generations and matching destination CRC32C
before refreshing expectations. A changed payload needs a new immutable document
and reviewed PR; follow the shared proposal Git sequence. Unchanged-plan replay
retains every original precondition and pinned executor. A merged body edit
never grants authority.

## Evidence and completion

| Question | Evidence to read before confirming |
|---|---|
| Naming, format, paths, identity candidates | Saved `plan`, `plan.blocking_questions`, `plan.curator_field_options`; `gcs_asset.py validate-path` exit/result |
| FGB/PMTiles valid | `vector_asset.py validate --help`, then its JSON `valid`, `errors`, `pmtiles_verify`, `pmtiles_show`, `decoded_feature_count`, `decoded_property_keys` |
| Metadata bundle valid | `validate_feature_metadata.py --help`, then zero exit and report `asset_slug`, `release`, `feature_count` |
| Schema compatible | `dataset_alerts.py check-schema-compatibility`: `compatible`, `blocked_diffs`, `waiver` |
| Docs/catalog current | `catalog_docs.py check` zero exit; `confirm document-asset` rereads frontmatter and returns `completed_step` or a specific error |
| Remote bytes/preconditions | `gcs_asset.py stat`: `uri`, `generation`, `size`, `crc32c`; distinguish not-found from authentication failure |
| Ready | Concierge `validate`: `ready_for_pr` / `ready_for_preview`, `errors`; readiness grants no human approval |

Keep real command logs and tool paths/versions; derive validation booleans from
those results. Admission, identity, translation and exception approvals remain
explicit curator decisions. Validators do not establish those decisions for you.
For explicit deletion requests only, read [reviewed-deletion.md](references/reviewed-deletion.md).
Report changed files, artifacts, source/version, paths/generations, commands,
retained local work directories, announcement state (sent/skipped/uncertain), and
anything unverified. A proposal does not claim that protected promotion ran.
