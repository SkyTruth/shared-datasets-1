# Change or add an ingestion deployment

Read [AGENTS.md](../AGENTS.md), the [deployment skill](../.claude/skills/deploy-scheduled-ingestion/SKILL.md), and, for Terraform, the [protected apply skill](../.claude/skills/protected-terraform-apply/SKILL.md). This procedure includes private usage telemetry; source behavior belongs in the owning job's README.

1. **Declare scope and ownership.** Name the target, resources and intended outcome. Follow [agent integration](agent-integration.md) for overlapping work and [publication readiness](publication-readiness.md) before expensive real-release work. New assets/pipelines require admission evidence and a feature identity decision under AGENTS.md.
2. **Register the producer.** `DEPLOY_TARGETS` in [`ingestion_targets.py`](../scripts/ingestion_targets.py) owns resource scope, runtime window, canary policy and verification hook. Its constructor rejects incompatible policies; `TARGETS` excludes telemetry. Use a thin `<target>-deploy.yml` wrapper around `ingestion-deploy.yml`; keep shared publication claims and installed identity state intact.
3. **Connect the deployment.** [`terraform-targets.json`](../.github/terraform-targets.json) owns deployment workflows/images, `terraform_prerequisites`, registered apply scopes and installed image checks. The same prerequisite graph must match CI callers' `needs` and conditional success gates; it orders selected owners without requesting unrelated mutations. Add resources using the [target-change procedure](terraform-reconciliation.md#change-a-terraform-or-iam-target). Do not duplicate input lists: selection follows workflows, nested actions, invoked scripts, Docker COPY and parsed Terraform ownership and modules. `selection_exceptions` is the single reasoned table for traversal boundaries, excluded validators and per-deployment input additions. Admission entrypoints stop traversal because their imports do not produce deployment content.
4. **Exercise the boundary.** Run focused positive and refusal tests for selection, prerequisites, plan scope and runtime verification. Production recipes and Terraform image consumers determine image bindings; register probes under `image_checks`. Missing typed executor environment keys fail before authentication. Every selected deployment retains its image validation floor, including hold-only releases. Use complete synthetic runtime/serialization batches for publication-code changes without a real release, and the production conversion chain for native changes. Follow [image contracts](deployment-contracts.md#images-and-execution) for CPU, memory, timeout and scratch; installed probes have no network/source mounts and use memory-backed `/tmp`. WDPA's 12-hour task timeout covers its observed 8 h 21 m maximum. Release at most one held ingestion target per change.
5. **Validate and review.** Follow [validation before push](ci-preflight.md#validate-before-push). Include expected actions, scope/permission coverage and unverified live prerequisites. Production mutations require `jonaraphael` review, merge to `main` and the protected `shared-datasets-production` workflow; local plans are review evidence. AGENTS.md still governs Git operations.
6. **Observe the rollout.** Main `ci-ready` supplies exact tested images by digest; deployments never rebuild missing bytes. Finish registry/IAM bootstrap first. Follow [queue ownership](deployment-contracts.md#serialization-and-protected-execution): preparation and canaries stay outside the state queue. Usage holds one target queue through apply and canary verification. Its read-only `dataset-usage` gate derives the composed apply job name from the YAML caller chain and observes this exact attempt’s signed apply job so ingestion/cleanup IAM can proceed while `dataset-usage-rollout` retains the queue. Other ingestion wrappers retain combined rollout. Recovery/dispatch requires `executor_sha`, `source_run_id` and `source_run_attempt` from the exact successful main-push CI attempt. Deferred verification is not completion.
7. **Report the outcome.** Use the captured canary execution, verify its [terminal outcome](deployment-contracts.md#records-receipts-and-runtime-outcomes) and release/latest contracts (or private usage report/activation), and preserve [failure coverage](alert-routing.md#execution-and-delivery-verification). Report image digest, resource actions, execution/result, changed remote paths and uncertainty. Use [recovery](ci-recovery.md) for failures.

Production identities are registered in [`github-workflow-identities.json`](../terraform/envs/prod/github-workflow-identities.json): exact workflow filenames on main, `job_workflow_ref` for reusable jobs, `workflow_ref` otherwise, repository/environment constraints. The separate PR planner requires exact CI/planner refs; advisory PR bucket reads admit only the exact schema-alert leaf at a numeric merge ref after the same-repository gate. Artifact Registry IAM bootstrap provisions the identity manager and workflow identity scope before writer rollout. The authoritative Terraform WIF binding removes the shared environment subject grant.

Observer identities cannot mutate resources, administer IAM, read state or access secret versions. Runtime handles image pushes, canaries, schedule control and invalidation; verification restores observer credentials afterward. Reconcilers have separate private incident-state authority; only the safety heartbeat identity emits heartbeat logs. Preserve signing and dataset approval boundaries.

For pause/resume, teardown and activation exceptions, use [job operations](../.claude/skills/deploy-scheduled-ingestion/references/job-operations.md). WDPA operations live in its [monthly runbook](wdpa-monthly-runbook.md), first identity installation in the [reset runbook](feature-id-reset-installation.md), and usage activation/cost gates in its [README](../ingestion/dataset_usage/README.md#activation-and-cost).

## Automatic read-only Terraform PR plans

The owner's 2026-11-05 decision authorizes automatic live planning for same-repository Terraform PRs before `ci-ready`, without an approval click. Application/docs changes skip. Selection and execution resolve the same registered production scopes, including manual IAM owners and removed declarations from the comparison base. Preview-only, lockfile-only and other unregistered Terraform changes emit a skip notice; static checks still apply.

Each scope uses pinned Terraform **1.8.5**, refreshed state and state-recorded immutable images. Saved plans pass production resource/action/image allowlists and permission validation. Policy Troubleshooter v3 evaluates the production deploy identity's inherited/conditional grants and deny policies; overall and allow verdicts must grant access. Unknown, missing or unreadable authority fails closed. This does not claim principal access boundary evaluation or replace deploy-time checks.

The PR identity can read metadata/IAM and the exact default production state object, plus bucket object names for GCS workspace discovery. It cannot write/lock state, mutate resources, read Secret Manager (including metadata/policies), sign or impersonate the deployer. The six reviewed `pr_plan_exclusions` identify secret-bearing scopes; each exclusion emits a notice while static checks and protected planning remain required.

**Same-repository PR authors can read sensitive values persisted in production state.** This is the owner's explicit exception to credential-free PR validation. Fork PRs skip authentication and normally receive no `id-token: write`; keep GitHub's fork write-token option disabled because the WIF PR subject alone does not distinguish forks. Other PR jobs remain credential-free.

The separate PR WIF pool requires this repository, `pull_request`, a numeric PR merge ref, the exact CI `workflow_ref` and reusable planner `job_workflow_ref` at that ref. Plans/JSON remain private temporary files, never uploaded; checkout credentials are not persisted. Logs name scopes, resource declarations/actions and permissions while withholding provider attributes and unclassified exception text.

Activate through the reviewed protected `terraform-state-read-iam-sync.yml`: `PR plan identity IAM bootstrap` precedes `PR plan identity provisioning`. Set `GCP_PR_PLAN_SERVICE_ACCOUNT` first, then `GCP_PR_PLAN_WORKLOAD_IDENTITY_PROVIDER` from the sensitive `github_pr_plan_*` outputs after provisioning succeeds. Without the provider variable the job explicitly reports **not yet activated**, succeeds and does not authenticate. Once configured, auth/plan/allowlist/permission failures block `ci-ready`. Code changes alone provision no identities; no local apply is permitted.
