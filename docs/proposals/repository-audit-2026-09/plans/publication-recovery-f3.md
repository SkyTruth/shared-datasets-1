# F3 — concrete adapter and guarded adoption plan

**F3a HOLD-only source accepted and frozen; F3b/c PLAN ONLY.** F1/F2 remain frozen in their separate review patches. CHARTER supplies the common gates. This plan proposes an opt-in managed rollout, not global atomic publication or automatic legacy migration.

Read for this revision: actual local/reviewed publishers, E's frozen envelope/helper/workflows, B's accepted baseline/output interface, all ingestion success/skip branches, metadata `patch` paths, localization uploads, index rebuild, catalog deployment, and Docker import lists. Skills applied: invariant-first, GCS, docs-sync, deploy-scheduled-ingestion, protected-terraform-apply, translations, publishing, and static catalog. No tools installed, remote API called, deployment/settings changed, or Git state mutated.

## 1. Scope and executable adoption fence

F2's complete-release protocol requires existing release-feature manifests. F3 will first manage `wdpa-marine`, `wdpa-terrestrial`, `ims-sea-ice-extent`, and the e-AMLIS vector asset, plus explicitly registered manual vector assets. It will not invent a data manifest for CSV/COG/Zarr or rewrite their formats.

Introduce checked-in `catalog/publication-rollout.json`, validated by `scripts/publication_rollout_gate.py`, with exact version, stage, and catalog-resolved managed asset/job roots. Initial stage is **hold**. Registration is authoritative even before remote state exists: a registered asset with absent/invalid state refuses every canonical write, with no legacy fallback. A detected publication state on an unregistered root also refuses legacy mutation and requires configuration reconciliation. Registration precedes adoption, and retirement does not silently remove this protection.

The three ingestion deployment workflows call the stdlib gate immediately after checkout, **before auth, image build/push, Terraform planning/apply, canary or Scheduler resume**. `hold` fails with a precise adoption-required result on push and dispatch; it is not a shell warning or an overridable env flag. Add the policy/helper paths to workflow triggers. This gate must merge with or before B/F2, whose shared source changes automatically trigger these deployments.

Two subsequent reviewed policy states are proposed: `install_guard` permits deploying only guarded images, requires read-only proof that the relevant Scheduler is paused and no old execution is running, and disables all canary/resume steps; `active` requires validated adoption readiness for every job-owned asset before permitting canary/resume. Preserve existing protected environment and Terraform resource allowlists. No local apply, new IAM grant, general Terraform refactor or live transition occurs in this assignment. The installed runtime independently refuses unadopted managed assets before any success, skip, metadata, run-record or index write.

Existing unadopted/unregistered assets retain the explicitly named **legacy path**, including F1 local source snapshots and original-generation finalizer CAS. Current manual CSV/COG/Zarr workflows therefore do not regress merely because managed vector rollout begins. They retain their current per-object/multi-object limitations and are not covered by managed recovery, reservation or chronology guarantees. An adopted asset may never use that path, even for an unsupported request: it fails `UNSUPPORTED_MANAGED_PUBLICATION` before mutation. General nonmanifest activation remains a separate protocol decision and F is not globally solved by this rollout.

Old deployed binaries, historical workflow reruns, and general break-glass credentials cannot be fenced by a Python library. External quiescence is a prerequisite before seeding state. If it cannot be established, leave the gate at hold; do not claim adoption readiness.

## 2. Frozen E handoff and actual execution entry

Stage no E/B source now. After approval, the supervisor supplies an integration source baseline containing accepted E+B and F1/F2 (and relevant G helpers when accepted), records their hashes, and retains their patches separately. F3 diffs are measured against that baseline; no duplicated E approval model or B allocator is introduced. Shared-file overlaps are limited to F-owned execution hunks described below.

The E workflow retains capture/verify and immutable executor checkout. Replace the current sequence of promote → live finalizer → independent index rebuild with one call:

```text
uv run python scripts/publish_workflow.py promote \
  --plan-json publish-plan.json \
  --authorization-envelope authorization/authorization.json \
  --authorization-sha256 <E gate output> \
  --receipt-report publication-result.json
```

The new `scripts/publication_adapter.py` checks envelope byte hash and E `validate_envelope`, requires outcome `mutation`, compares canonical plan JSON to `envelope.document.publish`, and calls E `identity_digests`/`executor_contract`. Context uses E proposal_key and execution_contract_sha256 directly. The trusted wrapper retains E's fresh live acceptance verification; a local self-written envelope is not permission to invoke canonical publication. No-mutation envelopes, foreign plans and executor mismatch refuse. The adapter passes `Executor.run(context, prepare=..., local_sources=...)`; only the core calls prepare when the original receipt is absent. An existing receipt is semantically checked against the same envelope before any source rebuilding or destination replanning.

Mode selection is internal, deterministic, and does not change E's plan schema: complete manifest bundle → complete_release; localized sidecars/translation CSV on a pinned committed release → metadata_update; byte-identical artifact restoration/README/index repair → object_repair; only the two global catalog payloads → catalog_update. Mixed one-asset plus global catalog remains supported. A second asset root or `release_index_asset_slugs` naming another asset refuses this v1 execution; users prepare a separate reviewed proposal. Unknown/global catalog targets cannot hide an asset index or schema snapshot.

Every explicitly approved target keeps its E destination generation (empty means 0), source generation and content/cache metadata. Preserve source provenance metadata (`asset_slug`, source/version/release/format fields) from generation-pinned source metadata, plus only explicitly defined runtime provenance; overlay reserved publication tags. Implicit run/index/schema derivations are restricted to the one asset and the named `finalize-promoted-release-v1` executor contract. Their destination generations are captured once inside first preparation and persisted, never reread as replacement authority on resume. If a plan explicitly names a derived destination, its approved expectation controls and only one operation exists.

Terminal replay reports original results without source existence requirements. Later workflow attempts use the same E proposal key. Changed executor refuses; no refreshed expectation or second transaction is synthesized. Remove the managed catalog-equality exception, in-loop schema uploads, and separate live finalizer/rebuild. The standalone finalizer refuses managed targets and remains F1-safe only for legacy assets.

## 3. Real semantic validation and deterministic derivation

Implement `ingestion/common/publication_bundle.py` (pure intent checks plus concrete byte preflight) and `ingestion/common/publication_derivation.py`. These are mandatory production callbacks, not test lambdas or a prevalidated flag. Version remains exactly `finalize-promoted-release-v1`; executor SHA binds the implementation.

First preparation downloads every staged object at its approved generation into F1-style private snapshots, hashes actual bytes, validates declared manifest/template hashes, and performs all domain/native checks **before the receipt or claim is created**. Ingestion builders use the same validation on their frozen outputs. Store the bounded immutable manifest/schema templates, baseline references, fixed timestamps, role/dependency map, schema-compatibility decision and pinned prior-index payload in typed derivation parameters. They bind the initial byte validation to the exact operation source hashes. Resume revalidates this full parameter schema, authorization mapping, closure, reservation and target policy from persisted intent; pending source operations verify exact bytes again. Terminal replay validates structural/authorization closure without requiring deleted source files.

| Mode | Concrete domain check |
|---|---|
| complete_release | One slug/release; FGB, PMTiles, canonical sidecar, schema and both manifests; exact role/path/digest map, optional extra formats explicitly declared. Run release_feature_model schema/manifest/sidecar validation; stream all FGB records to prove ID uniqueness and exact sidecar ID/hash/property correspondence; compare row count. Native validator must verify PMTiles archive, declared layer/properties and representative decoded tiles; tools absent means refusal. Representative tiles are not claimed to exhaustively prove all tile membership. Generated identity uses B snapshot and previous/next sequence; validate new/reused IDs and approved decisions against the pinned baseline, then core CAS checks persisted reserved high-water. Source-field strategy carries no range. |
| metadata_update | Pin canonical manifest/sidecar/schema plus translation source generations before work. G's local report must indicate valid and requested completion; compare ID set/hash columns, allowed translatable fields and source hashes to that immutable baseline. No base FGB/canonical sidecar/schema/manifest change, new IDs, or activation. Pass downloaded schema to G protected_inputs. |
| object_repair | Data can only restore a digest already declared by a verified committed manifest/adoption fact; no new ID, schema or release. README changes are explicit approved source bytes. Index-only repairs derive solely from committed receipts plus frozen adoption evidence. Run-only skipped records may add diagnostic status and latest-run data without changing latest-release identity. |
| catalog_update | Only `_catalog/shared-datasets-catalog.csv` and `_catalog/web/catalog.json`; validate shape, catalog roots and release facts against declared pinned committed index inputs/repo metadata. No per-asset index/schema snapshot or dataset write. This is a presentation refresh, not allocation/activation authority. |

Derivation switch has closed typed cases: manifest, run_record, release_index, schema_snapshot. No dynamic import or arbitrary function name. Manifest payload starts from the fixed approved template, replaces only declared artifact generation/size/content/latest-generation facts from prerequisite results, retains identity/schema/provenance, and excludes its self-generation. Use the same finalized bytes for release and latest manifests (latest can copy the prior manifest result). Run payload uses a fixed preparation timestamp and receipt results; index uses existing pure merge helpers with a fixed updated_at and pinned prior payload; schema snapshot uses the validated schema and fixed timestamp. No derive callback calls stat, clock, random, or fresh index discovery. Store JSON serialization as a fixed contract. Local checkpoint completion, not native rebuild determinism, provides durable bytes; absent uncheckpointed bytes remains NOT_RECOVERABLE_SOURCE with reservation retained.

Validators and native tools are runtime dependencies. Update explicit Docker script COPY lists and embed full executor source SHA as build metadata consumed by scheduled Context. Workflow validation must provide the existing repo-owned native toolchain (record paths/versions); an incomplete runner fails before writes. Local implementation tests may mock native invocation but the handoff must separately report runnable-tool integration coverage; no install/build/deploy is authorized here.

For scheduled jobs, request identity is stable `(writer_id, asset_slug, requested_release, upstream fingerprint, configuration digest)`, separate from executor SHA/attempt. A matching active request resumes its stored sources before fetching upstream; an incompatible executor refuses. Source discovery needed for a genuinely new request does not refresh an existing receipt. A same-day different source revision cannot silently become a new activation. Each WDPA asset has its own claim; cross-asset job completion remains non-atomic.

For the existing protected catalog deployment, a logical refresh request has a stable explicit request key (the original workflow run ID plus checkout SHA; attempts excluded). Retry uses that request, while an intentional new refresh is a distinct request. Add an explicit resume-request input for cross-run recovery rather than treating redispatch as retry. Resolve its global receipt before rebuilding or capturing generations. Pin downloaded index sources and fixed generated_at on initial preparation. The two payloads use one receipt; static files are not dataset commit authority. Competing global requests may conflict or produce presentation staleness; they cannot advance protected asset state. Global catalog refreshes do not make independent latest aliases atomic.

## 5. Notifications, adoption evidence, and rollout prerequisites

Managed publish removes automatic delete-scratch-sources. F2 has no delete proof; staged sources/checkpoints remain, with A's independent age policy explicitly unchanged. No receipt claims another worker's delete succeeded. Cleanup/reclamation is a separate exact-generation policy.

Combine the existing upload-summary and applicable breaking-change content into one immutable notification payload/delivery to fit the one F2 journal. After all required results, use begin_notification → send → finish_notification. Definite nondelivery can retry only with explicit retry_failed and a new attempt ID; transport uncertainty stays unknown and refuses automatic resend. The workflow's status/report command never republishes data. Cloud logs remain diagnostics. No Slack message is sent during implementation/testing.

Adoption is explicit, not a runtime fallback. Implement a **read-only** adoption preparation/validation command and fixture tests in `scripts/publication_adoption.py`; do not implement or run remote seed mutation in F3. Evidence must name exact current manifest/sidecar/schema/index generations and SHA, B high-water history/approved legacy decision, known historical index facts and absence/partial-release findings. Core adoption receipt evidence_sha256 binds the canonical evidence document. The initial seed's durable evidence storage and protected seed command require a separate small reviewed operational change before stage active; no code invents historical high-water. Recommended durable evidence path uses the already approved `publications/inputs/{adoption_key}/0.catalog.json` suffix for bounded frozen catalog/receipt evidence, with no newly allocated feature rows, written before the adoption receipt and state create. This exact evidence payload and seed order are approval blockers, not implemented schema assumptions.

Required deployment order: land hold gate; accept/integrate adapters and B; verify evidence; externally quiesce old binaries/manual historical writers; reviewed transition to install_guard; deploy guarded images with canary/resume disabled; approved seed process; verify all managed roots/receipts/high-water and no incomplete foreign claim; reviewed transition active; canary and validate through existing protected workflows. No production migration is performed by this coding task. If operational prerequisites are unavailable, F3 can be code-reviewed but the policy remains hold and B/F are not declared deployed/operationally complete.
